# Brief for the CRMS session: feeding credit bureau data to core banking

Date: 8 October 2026
Audience: the engineer or Claude session working in `C:\Users\fabiy\source\repos\crms`.
Scope: changes to CRMS only. Core banking (`C:\Users\fabiy\IdeaProjects\tpbackend`) already has everything described here; do not change it from the CRMS session.

## 1. Why this work exists

The bank submits a monthly return to the credit bureaus: one row per borrower and one row per loan. That return is now generated by **core banking**, not CRMS, because core banking holds the balances, arrears, repayments and classifications, and because some banks use core banking without CRMS.

A handful of the return's columns are facts that CRMS learns during origination and core banking never hears about. Today a member of staff would have to re-key them in core banking. This brief asks CRMS to send them when it books a loan.

**CRMS must not generate the return, store balances or arrears, or duplicate the bureau logic.** Its only job here is to hand over what it already knows.

## 2. What exists in CRMS today (verified by code review, 7 October 2026)

- `IFineractDirectService` / `FineractDirectService.cs` talks directly to core banking's REST API with Basic auth plus a `fineract-platform-tenantid` header.
- `BookApprovedLoanAsync` creates, approves and disburses a loan in three calls: `POST loans`, `POST loans/{id}?command=approve`, `POST loans/{id}?command=disburse` (or `disburseToSavings`). Callers:
  - corporate streamlined flow: `CompleteCorporateDisbursementHandler` in `CRMS.Application/LoanApplication/Commands/CorporateLoanRestructureCommands.cs`;
  - NAMP: `CRMS.Application/Namp/Commands/NampWorkflowCommands.cs`;
  - RH-SHF: `CRMS.Application/Rhshf/Commands/BookRhshfDisbursementCommand.cs`.
- The loan payload (`loanBody`, about lines 531-552 of `FineractDirectService.cs`) carries no CRMS reference.
- CRMS writes nothing else to core banking: no collateral, guarantors, consent or customer details.

Line numbers may have moved; search for the names.

## 3. What to build, in priority order

### 3.1 Send the CRMS reference when creating the loan

Add `externalId` to the `POST loans` body, set to a stable, unique CRMS reference for the application (for example the application number). Core banking stores it on the loan and enforces uniqueness.

- If a retry hits "external id already exists", look the loan up instead of failing: `GET loans?externalId={value}` returns it.
- This also closes the existing gap where a loan is created but approve or disburse fails, leaving a core banking loan that CRMS has no link to (`FineractDirectService.cs`, the two `catch` paths after the `POST`, about lines 605-642). On retry, find the loan by `externalId` and resume from the step that failed rather than creating a second loan.

### 3.2 Send consent and legal status for the loan

After the loan is created (any time; it does not have to be before disbursement):

```
POST datatables/Credit%20Bureau%20Information/{loanId}
{
  "locale": "en",
  "dateFormat": "dd MMMM yyyy",
  "BureauConsentStatus_cd_Consent Status": <codeValueId>,
  "BureauLegalChallengeStatus_cd_Legal Challenge Status": <codeValueId>,
  "Litigation Date": ""
}
```

- The datatable is one row per loan. If a row exists, use `PUT` on the same URL with only the fields that changed.
- The two dropdown fields take **code value ids**, which differ per bank. Resolve them once and cache: `GET codes` to find the code by name (`BureauConsentStatus`, `BureauLegalChallengeStatus`), then `GET codes/{codeId}/codevalues` and match on the `name` text ("Consent Available", "Consent Not Available", "No", "Yes").
- New loans normally go in as legal challenge "No". Litigation date stays empty unless there is a suit.
- **Consent has to be real.** CRMS has a `ConsentRecord` aggregate with a `CreditBureauCheck` consent type, but the review found no live screen or handler that creates consent records, only the seeder. Confirm that, and if true, capture consent in the origination flow for all three tracks (corporate, NAMP, RH-SHF) before sending it. Send "Consent Available" only when an active, unexpired, unrevoked consent of the right type exists for the borrower; otherwise send "Consent Not Available".

### 3.3 Send borrower details the customer record lacks

Core banking has two customer datatables, shown by customer type. Send what CRMS holds; leave out what it does not.

Individuals (NAMP applicants):

```
POST datatables/Credit%20Bureau%20Individual%20Details/{clientId}
```

Fields: `BureauTitle_cd_Title`, `BureauNationality_cd_Nationality`, `BureauMaritalStatus_cd_Marital Status`, `Place of Birth`, `BureauEmploymentStatus_cd_Employment Status`, `BureauOccupation_cd_Occupation`, `BureauBusinessCategory_cd_Business Category`, `BureauBusinessSector_cd_Business Sector`, `Tax ID`, `Employer Name`, `Employer Address Line 1`, `Employer Address Line 2`, `Employer City`, `Employer State`, `Employer Country`, `Work Phone`, `Home Phone`.

Businesses (corporate and RH-SHF borrowers):

```
POST datatables/Credit%20Bureau%20Business%20Details/{clientId}
```

Fields: `BureauBusinessCategory_cd_Business Category`, `Tax ID`.

- `_cd_` fields take code value ids, resolved as in 3.2 from the code named before `_cd_`.
- CRMS holds occupation, employer and employment status as free text for NAMP, and industry sector as a fixed list for corporate. Map to the code values by exact, case-insensitive text. **If there is no match, omit the field; do not guess and do not create code values.**
- Do not overwrite: if the customer already has a row (`GET` returns data), send a `PUT` containing only fields that are currently empty in core banking.
- CRMS does not hold business size category, marital status or spouse. Leave them; bank staff capture them in core banking.

### 3.4 Send collateral

Core banking reports "Loan Security Status" by comparing the value of collateral on the loan with the outstanding balance, and prints the collateral type and description.

Use the loan collateral endpoint, which accepts a type, a value and a description:

```
POST loans/{loanId}/collaterals
{ "locale": "en", "collateralTypeId": <codeValueId>, "value": 25000000, "description": "Plot 12, ..." }
```

- **It is only accepted while the loan is submitted and pending approval.** Call it between `POST loans` and `?command=approve`.
- `collateralTypeId` is a code value of the code named `LoanCollateral`. Resolve by name as in 3.2. The bank should name those values after the bureau's ten collateral types (Real Estate/Land & Building, Automobile, Plant and Equipment, Natural Reserves, Marketable Securities, Accounts Receivables and Inventory, Cash, Personal Guarantees, Post Dated Cheques, Dormicilliation), because the return prints the code value's text. Map CRMS's `CollateralType` enum to those names in configuration, not in code.
- Send `value` as CRMS's acceptable value (after haircut), falling back to forced sale value, then market value. Send only collateral that is perfected or accepted for the facility.
- Do **not** use the other collateral mechanism (`clients/{id}/collaterals` plus a `collateral` array in the loan body). It rejects any loan whose collateral is worth less than the principal, so partly secured loans could not be booked.

### 3.5 Send guarantors

```
POST loans/{loanId}/guarantors
{ "locale": "en", "dateFormat": "dd MMMM yyyy", "guarantorTypeId": 3,
  "firstname": "...", "lastname": "...", "dob": "...", "addressLine1": "...", "city": "...", "mobileNumber": "..." }
```

`guarantorTypeId` 3 is an external guarantor. A loan with guarantors and no collateral is reported with collateral type "Personal Guarantees". Core banking's guarantor record has no BVN field; keep the BVN in CRMS.

### 3.6 Record the previous account when a loan replaces another

If CRMS ever books a loan that replaces an earlier one (restructure, refinance), tell core banking which account it replaces so the bureau can link them:

```
PUT tp/bureau/previousreferences
{ "accountNo": "<new loan account number>", "previousAccountNo": "<old loan account number>",
  "previousCustomerId": "", "previousName": "", "previousBranchCode": "" }
```

CRMS does not model restructures today (`CorporateLoanRestructureCommands.cs` is misnamed), so this is only needed if that is added.

### 3.7 Tidy-ups found in the review (same area, small)

- **Legacy corporate path** (`ApproveDisbursementHQCommand`): a user types a core banking loan id that is never checked. Validate it with `GET loans?accountNo=` or `GET loans/{id}` and store the real id and account number.
- **Closing a loan** (`MarkAsClosed`, `NampApplication.Close`, `RhshfCreditProfile.MarkClosed`) is a manual tick. Check the loan's status in core banking first and refuse if it is still active there.
- Several CRMS docs still say the integration is mock-only or manual. Update them once this is done.

## 4. Rules for all of the above

1. **Booking must never fail because of this.** Disbursement is the business-critical step. Each call in 3.2 to 3.6 is best-effort: on failure, log it, record it against the application, and carry on. Provide a retry (the existing outbox/background-service pattern fits) and a way for staff to see which items did not reach core banking.
2. **Idempotent.** Every call must be safe to repeat: check for an existing row and switch to `PUT`, or treat "already exists" as success.
3. **Maker-checker.** Where the bank has maker-checker switched on, a datatable `POST` returns success with a pending command rather than saving. Treat that as "sent, awaiting approval", not as an error, and do not resend.
4. **Permissions.** The core banking user CRMS signs in as needs: create and update on the three datatables (`CREATE_Credit Bureau Information`, `UPDATE_Credit Bureau Information`, and the same for `Credit Bureau Individual Details` and `Credit Bureau Business Details`), read on codes, create on loan collateral and guarantors, and `UPDATE_TPBUREAUCONFIG` if 3.6 is used. List these in the deployment notes; do not use an all-functions account.
5. **Branch scope.** Core banking refuses datatable calls for customers or loans outside the calling user's branch hierarchy with a 404 "data not found". The CRMS service user should sit at head office.
6. **No hard-coded ids.** Code value ids, product ids and datatable contents differ per bank. Resolve by name at runtime and cache.
7. **Mocks.** Extend `MockFineractDirectService` so the new calls work with `UseMock: true`, and cover the mapping and the failure-does-not-block-booking rule with tests.
8. **Single bank assumption.** CRMS is hard-wired to one bank today. Do not add more of that; keep new settings in configuration.

## 5. Suggested shape in the code

- Add methods to `IFineractDirectService` for each call (resolve code values, upsert loan bureau information, upsert customer bureau details, add loan collateral, add guarantor, save previous reference), with real and mock implementations.
- Extend the booking request with the CRMS reference, collateral and guarantor lists, and have `BookApprovedLoanAsync` send collateral between create and approve.
- Add one application-level service, called by all three track handlers after a successful booking, that sends 3.2, 3.3 and 3.5 and records the outcome per item.
- Persist a small "core banking sync" record per application (item, status, last error, attempts) for the retry and for the staff view.

## 6. How to know it works

For a loan booked from each track with collateral, a guarantor and consent:

1. In core banking, the loan shows the CRMS reference as its external id.
2. The loan's **Credit Bureau Information** tab shows consent and legal status.
3. The customer's **Credit Bureau Individual Details** or **Credit Bureau Business Details** tab shows what CRMS holds.
4. The loan's collateral and guarantor lists show what CRMS sent.
5. Reports → Extensive Reports → CREDIT BUREAU RETURN for that month prints those values on the loan's row, and the Exceptions sheet does not list the loan.
6. Killing the connection between create and approve, then retrying, ends with one loan in core banking, linked to the application.
