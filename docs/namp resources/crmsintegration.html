01

Business context

The RH-SHF portal lets FACs (Farmer Aggregator Companies) apply for input-financing under a programme (e.g. “Renewed Hope – Dry Season 2026”) for a given session / farming season. A FAC builds an EOP — a set of input line items, one per commodity (maize, sorghum…), each with a quantity and price, which sum to a total EOP value.

Before that plan can proceed to financing, the FAC must pass a credit check on your CRMS. The governing rule:

The rule

The FAC's total EOP value for a programme + session equals the loan amount the FAC is profiled for on the CRMS — exactly. EOP processing continues down the line only when the CRMS returns a positive approval.

Where the integration sits in the portal flow:

  1. FAC creates its per-commodity EOP records.
  2. FAC clicks “Submit for processing” — declaring its complete EOP set for the programme+session (this locks further EOP creation).
  3. A BOA admin vets the submission — may return it to the FAC for changes, or certify it.
  4. On certification, the portal calls your CRMS — this integration begins.
  5. Positive CRMS approval → EOP processing continues downstream (credit paper, offer letter, supplier orders…).

You are integrating at steps 4–5. Everything before step 4 is internal to the portal.

04

The contract

All bodies are JSON (application/json). Base URLs, credentials and the portal callback/origin are exchanged per environment (sandbox and production) during onboarding.

4.1  Submit consolidated EOP

POST{CRMS_BASE_URL}/v1/credit-profiles

Called once, when a BOA admin certifies the FAC's EOP set.

  • Auth (portal → CRMS): choose one and tell us — OAuth2 client-credentials (preferred), a static API-key header, or mTLS. We send whatever you specify.
  • Idempotency: the portal sends an Idempotency-Key header (also submissionId in the body). Re-sending the same key must return the same case/token, never a duplicate.

The portal opens the form as {profilingUrl}?token={token} in a new tab on the CRMS domain. If you'd rather return the complete URL with the token already embedded, return profilingUrl fully-formed and say so. Errors use standard HTTP codes with a JSON body { "error": "code", "message": "human text" }.

4.2  The secure reference token

  • A signed, JWT-shaped token issued and verified by the CRMS (your signing key; the portal never verifies it — only carries and forwards it).
  • It names the session; it does not store progress. Keep the FAC's live stage server-side on the CRMS, keyed by the token's subject. On load: verify token → look up the case → render the current stage. Don't bake mutable progress into an immutable token.
  • Short-lived and refreshable — it travels in a URL query string, and URLs leak (browser history, proxy/server logs, Referer). Suggested lifetime 15–30 min; single-use or rotate on load. If the FAC opens the link after expiry, the portal calls token-refresh (4.6) first.
  • Suggested claims: sub (case/reference), facId, programme, aud, iat, exp, jti. Bind it to the case so a token for case A can never open case B.

4.3  Profiling form (CRMS-hosted, opened on the CRMS domain)

The FAC completes profiling on your form, on the CRMS domain — opened in a normal browser tab, not embedded in an iframe. Requirements:

  1. Accept the token from the token query-string parameter; verify it; resume at the FAC's current stage. Your form keeps its own session/cookies normally — first-party, on your own domain (no SameSite=None gymnastics).
  2. Handle expiry gracefully — on an expired/invalid token, show a friendly “session expired” page telling the FAC to return to the portal and reopen the link (the portal mints a fresh token via 4.6).
  3. On completion, show a clear “submitted — you can close this tab” confirmation. The portal learns the outcome from the webhook (4.4) and reflects live status from the status API (4.5); no postMessage bridge is required.
Why not an iframe?

We evaluated embedding the form in the portal and dropped it. Iframing depends on your pages allowing frame-ancestors for our origin — which secure/banking systems usually block (X-Frame-Options: DENY|SAMEORIGIN) — and it adds third-party-cookie and cross-origin-messaging complexity. Accessing the form directly on the CRMS domain removes that risk entirely, and the status API + webhook already give the portal everything it needs to track progress.

How the FAC reaches it: the portal is the authenticated hub — the email links back to the portal, the FAC logs in and sees a CRMS-profiling page showing current status and a “Continue on CRMS” button that opens your form (new tab) with a fresh token. Your form is always reached via a fresh, portal-issued link — never straight from the email — which lets the portal refresh the token just-in-time and keep the FAC's status view in one place.

4.4  Outcome webhook

POST{callbackUrl} CRMS → Portal

Call the callbackUrl from 4.1 whenever the case reaches a terminal decision, and (recommended) on notable status changes.

Signing (required): sign the raw body with a shared secret (exchanged out-of-band) and send the signature in a header, plus a timestamp to prevent replay:

X-CRMS-Signature: sha256=<hex HMAC-SHA256(secret, rawBody)>

Portal responds 2xx on receipt. Please retry with backoff on non-2xx / timeout (e.g. 5 attempts over ~30 min); make delivery idempotent via eventId.

4.5  Status query

GET{CRMS_BASE_URL}/v1/credit-profiles/{reference}/status

Lets the portal poll and reconcile if a webhook is missed. Same portal→CRMS auth as 4.1.

4.6  Token refresh (optional, recommended)

POST{CRMS_BASE_URL}/v1/credit-profiles/{reference}/token

Returns a fresh { token, tokenExpiresAt } for an existing case, so a FAC who opens an expired email link — or returns days later to continue — can resume.

Case status (returned by 4.4 / 4.5):

StatusMeaning
RECEIVEDSubmit accepted; case created.
PROFILING_PENDINGAwaiting the FAC to open the profiling form.
PROFILING_IN_PROGRESSFAC is completing the form.
UNDER_REVIEWCRMS is assessing.
APPROVED / DECLINED / INFO_REQUIREDTerminal (or action-needed) decision states.
EXPIRED / CANCELLEDCase lapsed or withdrawn.

Decision outcome: APPROVED · DECLINED · INFO_REQUIRED.

For context, the portal's own states move: SubmittedForProcessing → UnderBOAReview → (ReturnedToFAC | Certified) → CRMSProcessing → CRMSApproved | CRMSDeclined. Your statuses drive the CRMSProcessing → CRMSApproved/Declined transition.

08

Non-functional expectations

  • Idempotency: submit is idempotent on Idempotency-Key / submissionId; webhook is idempotent on eventId.
  • Retries: webhook retried with backoff until 2xx; the portal also polls 4.5 as a safety net.
  • Timeouts: portal→CRMS calls respond within a few seconds; long work happens asynchronously and is reported via webhook / status.
  • Timezones: all timestamps ISO-8601 UTC (Z).
  • Versioning: path-versioned (/v1/…); additive changes only within a version.
  • Correlation: reference (and submissionId) appear on every touchpoint for tracing.
09

Acceptance criteria

Definition of done for the CRMS side.

  1. POST /v1/credit-profiles accepts the 4.1 payload, is idempotent, and returns reference, a valid short-lived signed token, and profilingUrl.
  2. The profiling form, opened as {profilingUrl}?token=… on the CRMS domain, authenticates via the token and resumes at the correct stage.
  3. Expired/invalid token → graceful “session expired” page directing the FAC back to the portal; token-refresh issues a new one.
  4. On decision, CRMS calls the callbackUrl with a valid HMAC signature, retrying until 2xx, idempotent on eventId.
  5. GET /v1/credit-profiles/{reference}/status returns current status / stage / decision at any time.
  6. A sandbox environment is available for the portal team to test all four touchpoints end-to-end before production.

Open items to confirm

  • Whether profilingUrl is a base URL (portal appends ?token=) or fully-formed.
  • Resolved: the CRMS form is accessed directly on the CRMS domain (no iframe), reached via the portal hub — the FAC clicks “Continue on CRMS” from an authenticated portal page, never straight from the email; the portal tracks progress via the status API + webhook.

Using this with an AI assistant

This brief is written to be handed straight to an AI coding assistant (e.g. Claude). A good starting prompt for your team:

“You are helping build the CRMS side of an integration described in the attached brief. Our stack is [your language / framework / DB]. Implement, with tests: (1) POST /v1/credit-profiles — validate the payload, create a credit-profiling case, be idempotent on submissionId, and return a short-lived signed reference token per §4.2; (2) token issuing/verification and a refresh endpoint (§4.6); (3) the token-authenticated, resumable profiling web form (§4.3), hosted on your own domain, that keeps progress server-side; (4) the HMAC-signed outcome webhook caller with retries/idempotency (§4.4); and (5) the status endpoint (§4.5). Use the exact JSON shapes and statuses in the brief. Flag anywhere our existing system makes a different choice more natural, and list the values you need from the portal team (auth, origins, secrets).”

Ask the assistant to keep to the JSON field names and status vocabulary above so both sides line up, and to surface any deviation explicitly so we can reconcile the contract.
